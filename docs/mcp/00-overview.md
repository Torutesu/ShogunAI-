## 重要な前提の訂正

Issue #59 は「MCP を繋ぐ仕組みがまだ存在しない」前提で書かれているが、**実際には接続レイヤーの大部分がすでに実装済み**である（2026-07 時点）。

- `crates/shogun-mcp` — 権限表・認可ゲート・接続状態機械・JSON-RPC サーバー（純ロジック、テスト済み）
- `crates/shogun-integrations` — 公式 MCP エンドポイント定義・OAuth 2.1+PKCE・トークン管理・Keychain・同期ランタイム
- 設計の正本は `docs/requirements-v1.0.md` §6.9〜6.10（FR-INT-01〜07 / FR-C2-01〜05）

したがって本ドキュメント群の役割は「ゼロからの設計」ではなく、

1. **実在するアーキテクチャの言語化** — コードに埋まっている設計判断を、PM・ユーザー案内に使える形で取り出す
2. **案内の穴埋め** — ユーザー向けガイドとオンボーディング設計はまだ無いので、ここで定義する
3. **残作業の切り出し** — 未検証・未完成の部分（ライブ接続検証、UI 仕上げ等）を後続 Issue にする

残作業の正確な区分は `01-architecture.md` の「未検証事項」を参照。「未実装」と「未検証」を混同しないこと。

## 初期対応する MCP（Issue の「最大3〜5個」への回答）

段階導入（Wave 方式、FR-INT-03）がすでにコード化されている（`crates/shogun-mcp/src/scope.rs` の `Wave` enum）。

| Wave | サービス | Issue のカテゴリ対応 | 状態 |
|---|---|---|---|
| **Wave 1（初期ローンチ）** | Gmail / Google Calendar / Google Drive | カレンダー系・ドキュメント系 | 実装済み・ライブ検証待ち |
| Wave 2 | Slack | — | コードあり・未テスト |
| Wave 3 | Notion / GitHub / Linear | タスク・Issue 系 | コードあり・未テスト |

**初期対応は Wave 1 の 3 個**。Issue の「最大3〜5個」の枠に収まる。未リリースの Wave は認可ゲート（`service_gate::authorize_op`）が自動拒否し、UI では「Coming soon」表示になる。

## 用語定義

| 用語 | 意味 |
|---|---|
| **第1層** | 各サービスの**公式リモート MCP サーバーに直結**する経路。中間サーバー無し（FR-INT-01）。読み取り同期と書き込みの基本経路 |
| **第2層** | **Composio 経由**の経路。現状は Gmail 送信のみ。オプトイン必須で、第三者経由であることを UI に明示する（FR-C2-01〜05） |
| **Wave** | サービスの段階導入スケジュール。Wave 1 → 2 → 3 の順でしか解放されない |
| **接続状態（FSM）** | サービスごとの `connected` / `amber`（トークン失効など要再認可） / `disconnected` の状態機械 |
| **L3** | 外部への送信・書き込みに必須の人間承認レベル。承認キューを通らない外部送信は存在しない |
| **draft-stop** | Gmail 送信を「下書き作成まで」で止める安全設定 |
| **スコープ表** | `scope.rs` にある「サービス × Wave × 操作」の権限表。**表にない操作はすべて拒否**。権限の唯一の中心 |
| **オプトイン** | Composio（第2層）利用の明示的同意。同意なしでは第2層の同期・送信はスキップされる |

## スコープ / Non-Goal

**このドキュメント群でやること：**

- MCP 接続レイヤーの全体像を、実コードと対応づけて言語化する
- ユーザー向けの接続フロー（オンボーディング・設定画面）を定義する
- モデル（Claude）側から見た MCP 利用の設計（一覧の渡し方・呼び出し優先度）をまとめる
- 後続の実装 Issue を切り出せる状態にする

**やらないこと（Non-Goal）：**

- Wave 2/3 を含む 7 サービス以上の同時サポート設計（初期は Wave 1 の 3 個に集中）
- MCP プロトコル仕様そのものの解説や、各外部サービスの詳細 API 設計
- UI のビジュアルデザイン確定（ワイヤー骨格まで。仕上げは Figma / 別 Issue）

## 設計の核（詳細は 01-architecture.md）

1. **第1層 / 第2層の分離** — 公式 MCP 直結を基本とし、公式に無い能力（Gmail 送信）だけ第三者（Composio）で補う。第三者経由は必ずオプトイン＋UI 明示
2. **Wave 段階導入** — 少数のサービスを確実に動かしてから次を解放する。コードで順序を強制
3. **トレーサビリティ** — 外部とのやり取りは本文なしのダイジェストで記録し、ユーザーが後から確認できる
4. **秘匿情報は Keychain のみ** — OAuth トークン・API キーは macOS Keychain に保存。設定ファイルには置かない
