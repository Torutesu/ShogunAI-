# MCP 連携 — プロダクト / PM 向け設計

> Issue #59 のアウトプット第3弾。オンボーディングでの提案ロジック、初期対応数と選定方針、そして「MCP 連携がプロダクト指標にどう効くか」の検証設計。
> アーキテクチャの詳細は `01-architecture.md`、ユーザー体験の詳細は `02-user-guide.md`。
> 前提：**Gmail は読み取り・ドラフト・送信のすべてが Composio 経由**（2026-07 決定）。プライバシーの語り方・オンボーディングの同意設計・指標がこの決定で変わっている。

## 1. MCP ハブの役割（PM 視点の要約）

- ShogunAI は**自社の中間サーバーを持たない**。Calendar / Drive のデータは端末と各サービスの公式サーバーの間だけを流れる
- **Gmail は例外で、読み取りを含むすべてが Composio（第三者サービス）を経由する**（2026-07 決定、CLAUDE.md に記録済み）。理由は Gmail 公式リモート MCP が Developer Preview で実接続確度が低いこと — 「繋がらない直結」より「動く第三者経由 + 誠実な開示」を選んだ。必ず opt-in 3開示同意（同意前は同期ゼロ）・L3 + draft-stop 既定 ON・読み取り egress の本文なし記録が付く
- 「どのサービスで何ができるか」の権限は1枚の表（`scope.rs`）に集約されており、**表に無い操作は構造的に実行できない**
- 外部への送信は必ず人間の承認（L3）を通る。「AI が勝手にメールを送る」事故は構造上起きない
- 営業・サポート・LP でのプライバシー説明の核は次の3点：**(1) 自社サーバー無し (2) Gmail の第三者経由は隠さず、同意前は一切同期しないこと (3) 承認なしの送信は構造上不可能**。「すべて直結」という一律の主張は**しない**（Gmail 全面 Composio 化後は虚偽になる）

## 2. 初期対応数と選定方針

### なぜ 3 個か（Wave 1 = Gmail / Calendar / Drive）

1. **認可系統が2系統で済む**：Calendar / Drive は GCP の consent 画面1つ（`docs/oauth-client-setup.md` の手順1本）、Gmail は Composio API キー + user id の1組のみで **Google Cloud OAuth 審査の対象外**。Gmail が OAuth 系統から外れたことで、審査リスクの高い `gmail.*` スコープを審査プロセスから切り離せた
2. **「仕事の文脈」の3要素（予定・連絡・資料）が最小構成で揃う**。会議準備ユースケース（calendar → drive → mail）が3つで完結する
3. Issue #59 の「最大3〜5個」の下限に収め、**接続成功率・同期安定性を検証しやすくする**

※ Wave 1 = 3サービス（Drive 含む）は 2026-07-23 のプロダクト判断（`scope.rs` に記録）。`docs/requirements-v1.0.md` FR-INT-03 と CLAUDE.md Phase 1 の「Wave 1 = Gmail + Google Calendar」はこの判断に未追従 — 要件書側の更新を後続 Issue とする（本ドキュメント群では 3 サービスを正とする）。

### 次を解放する判断（Wave 2 = Slack、Wave 3 = Notion / GitHub / Linear）

- 解放の順序はコードで強制されている（`Wave` enum）。**いつ解放するかは人間の判断**で、コードに自動昇格は無い
- 目安（`connector-summary-and-live-checklist.md` より）：Wave 1 の接続成功率 95% を2週間維持
- 判断材料に加えるべきもの：接続ユーザーの継続率差分（§4）、サポート問い合わせの傾向、Slack 公式 MCP の安定性

## 3. オンボーディングでの MCP 提案ロジック

### 提案の原則

- **推奨は2つまで**（Calendar + Mail）。3つ全部を等価に並べると選択負荷で離脱する。Drive は「あとから Settings で」枠
- **順番は「即効性 × 信頼コスト」順**：Calendar（直結・OAuth だけ・接続10秒後に「明日の予定は？」が刺さる）→ Mail（文脈理解は深いが、**第三者経由の 3開示同意という一段重い判断**を伴う）→ Drive（単体の即効性が薄い）
- **信頼の非対称を設計に織り込む**：旧設計では Gmail も「読み取りは直結」と言えたが、現設計では **Gmail 接続 = 第三者経由への同意**。だからこそ Calendar を先に置き、「SHOGUN は正確に開示するプロダクトだ」という信頼を直結サービスで先に成立させてから Mail の同意判断をしてもらう。Mail の行には接続前から "via Composio" を明示し、同意シートで初めて知らせる不意打ちをしない（`02-user-guide.md` §2）
- **スキップを妨げない**：接続ゼロでもオンボーディングは完了できる。Mail の同意を渋ったユーザーを追わない（後述の同意率で計測し、文言・タイミングで改善する）。ただしスキップ率は計測する（§4）

### 初回体験の「アハ・モーメント」設計

接続直後の最初の1問で価値を体験させる。接続完了画面 or 初回チャットで、接続済みサービスに応じたサンプル質問を提示する：

| 接続したもの | 提示するサンプル質問 |
|---|---|
| Calendar | *"What's on my calendar tomorrow?"* |
| Calendar + Mail | *"Help me prep for my next meeting."* |
| Mail | *"Anything I need to reply to?"* |

この提示ロジックは軽い実装（接続状態を見て文言を出し分けるだけ）で、体験の立ち上がりに最も効くと想定。Mail のアハ・モーメントは**同意完了後にしか発生しない**ため、Calendar 単体のアハ・モーメント（同意不要・最速）を最初に確実に踏ませることが、Mail 同意率の前提になる。オンボーディング実装 Issue に含める。

### Gmail の同意を「いつ」求めるか — 読み取り同意と送信解放を分ける

旧設計の「Composio の同意は送信したくなった時点まで遅延する」は**成立しない**。現設計では Composio 同意（3開示）が無ければ**読み取り同期すら始まらない**ため、Mail を繋ぐならオンボーディング（またはユーザーが Mail を繋ぐと決めた瞬間）に同意が必要になる。そこで同意判断を2段に分ける：

1. **読み取りの同意（3開示）** — Mail の Connect 時。これが無ければ何も起きない。開示は正確に・怖がらせず・盛らずに（文言は `02-user-guide.md` §2-3'）
2. **送信の解放（draft-stop OFF）** — オンボーディングでは求めない。「返信を下書きした → 送りたい」という文脈が生まれた時点（Approvals 文脈）で初めて案内する。送信解放後もすべての送信は L3 承認を通る

初回の信頼残高が少ない段階で求めるのは 1 だけ。2 を初回に混ぜると、読み取り同意まで警戒されて接続率を落とす。

## 4. 検証したい指標（Issue #59 の Why への回答）

「MCP を繋いだユーザーがどれだけ LTV / 継続 / 満足度が上がるか」を検証するための最小セット：

| 指標 | 定義 | 見たいこと |
|---|---|---|
| 接続率 | オンボーディング完了者のうち1つ以上接続した割合 | 提案 UI の効き。スキップ率とセット |
| 接続深度 | 接続サービス数の分布（0 / 1 / 2 / 3） | 推奨2つ提示が機能しているか |
| **Gmail 読み取り同意率** | Mail の Connect を押したユーザーのうち 3開示同意を完了した割合（同意シート表示 → 承諾/離脱） | **第三者経由の開示がどれだけ受容されるか**。全面 Composio 化の実運用上の最重要リスク指標。離脱点（どの開示で止まるか）も見る |
| 接続→初回利用 | 接続後24時間以内に MCP 由来の回答を1回以上受けた割合 | アハ・モーメント設計の効き |
| 継続率差分 | 接続数別の W1 / W4 継続率 | **本命**。「接続 = 定着」の仮説検証 |
| amber 復帰率 | amber になったユーザーが再認可まで到達する割合 | 接続の壊れやすさ・案内の効き |
| 送信解放率 | 同意済みユーザーのうち draft-stop を OFF にした割合と、その後の承認/拒否比率 | 第2層の信頼獲得度合い（読み取り同意率とは別段階として計測） |

注意：計測はプライバシー設計（Issue #28 系）と整合させる。内容は一切取らず、接続状態とイベント種別のみ（同意シートの離脱点も「どの画面まで進んだか」のみ）。

## 5. リスクと構え

| リスク | 構え |
|---|---|
| Google 公式 MCP のツール名・挙動が変わる（Calendar / Drive） | ハブ操作名を安定 IF にしてある（`01-architecture.md` §5-2）。影響は toolmap の張り替えのみ |
| OAuth 審査（本番公開時） | 対象は Calendar / Drive のみに縮小済み（Gmail は Composio 経路で `gmail.*` スコープの審査対象外）。Testing mode で先に検証。審査は Wave 1 ライブ検証の後に着手 |
| 「メールが第三者を通る」への心理的抵抗 → Mail 接続率低下 | 隠さない・盛らないが唯一の構え：接続前からの "via Composio" 明示、3開示の正確な文言、同意前は同期ゼロ、本文なしトレーサビリティ、いつでも取り消し可能。Calendar 先行で信頼を積む（§3）。同意率と離脱点を計測して文言を磨く |
| Composio 依存（Gmail の全経路） | 単一障害点かつ第三者リスク。Gmail 公式 MCP が **GA になれば読み取り/ドラフトを第1層へ戻す**方針を明文化済み（CLAUDE.md / `01-architecture.md` §4）。ハブ操作名 IF のおかげで経路の戻しも toolmap 張り替えが中心 |
| Composio の障害・仕様変更 | Mail のみ amber/エラーに落ち、他サービスは影響を受けない（サービス独立の FSM）。障害時の文言は「SHOGUN ではなく経路の問題」と分かる形に |

## 6. 要オーナー判断（本ドキュメントでは未解決のまま記録する）

- **プラン境界と Gmail 読み取りの整合**：CLAUDE.md のプラン構成は「Standard = 第1層連携（読み取り）」「Pro = ＋Composio 第2層」。Gmail 読み取りが第2層（Composio）へ移った結果、字義どおりに読むと **Standard では Gmail が読めない**ことになり、Standard の価値提案（Wave 1 読み取り一式）と衝突する。「Gmail 読み取りは Standard に含める（Composio のうち読み取りのみ Standard 扱い）」か「Gmail は Pro 専用」かはプラン設計の判断であり、本ドキュメント群では決めない。**オーナー判断が出るまで課金ゲートの実装に着手しないこと**
