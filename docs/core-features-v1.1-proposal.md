## 0. 本書の目的と位置づけ

requirements-v1.0（最終更新 2026-07-19）の後に、次の3つが起きた:

1. **ポジショニングの明確化**: 「コンテキストレイヤーの覇権を取る」。競合（Coast / Nessie / Unabyss / Dex 等）の同時期参入により、(a) OSレベルキャプチャ、(b) 全AIモデルへのコンテキスト配布、(c) 覚えた上で自分で動く、の3点を**同時に**見せることがGTMの中心命題になった
2. **実装監査によるスコープ確定（2026-07-25）**: AIツール履歴取り込み・スレッド・参照解決・DB暗号化を**v1でやる**と決定済み。しかし requirements-v1.0 に対応するFRが存在しない
3. **コア機能の言語化**: マーケ側で確定したコア機能リスト（§1）に対し、要件側に欠けている機能・位置づけが弱い機能がある

本書は「v1.1としてrequirements-v1.0に取り込むべき差分」を、既存FR体系と同じ粒度で提案する。**本書自体は要件の正本ではない**。§6のオーナー判断が済み次第、requirements-v1.0への改版（`docs:` コミット）として反映する。

## 1. コア機能セット（v1.1提案）

マーケ側で言語化された6機能と、ポジショニング・実装監査から導かれる追加3機能を統合し、コア機能を9つに再定義する。

| # | コア機能 | 一言 | 現行要件 | 状態 |
|---|---|---|---|---|
| C1 | **パッシブキャプチャ（録らない設計）** | 裏側で静かに、テキストだけを取り続ける。スクショ・録画・録音を作らない | FR-CAP群 | ✅ 要件・実装とも存在。**差別化コピーの核**として§2.1の補強のみ |
| C2 | **ワールドモデル** | event log → state tables（provenance + confidence）＋スレッド＋名寄せ。「記録」ではなく「状態」 | FR-MEM群 / FR-ST群 | ⚠️ スレッド（threads / thread_key）が要件に未記載（実装は先行）→ §2.2 |
| C3 | **ユニバーサル・コンテキスト配布（ShogunMCP）** | 構築したコンテキストを、ユーザーが使う**すべてのAI**（Claude / ChatGPT / Cursor / 各種エージェント）に構造化して渡す | FR-API群（Memory API） | ⚠️ 存在するが「Proのおまけ」の位置づけ。**ヘッドライン機能への昇格と配布3経路の拡充が必要** → §2.3 |
| C4 | **AIツール間コンテキスト統合** | Claude Code / Codex / ChatGPT等とのやりとりを取り込み、モデル間でコンテキストが途切れない | なし | ❌ **要件に存在しない**（監査でv1決定・一部実装済み）→ §2.4 新規FR-AIS群 |
| C5 | **⌥ワンアクション実行** | Optionキー起点の最短実行。「ボタンを押せば仕事が終わる」の物理形 | FR-NU-01（⌘⇧Space）/ FR-CF群 | ⚠️ ホットキーはあるが「⌥一発で最上位アクション実行」は未定義 → §2.5 |
| C6 | **会議ノート（botなし・録らない議事録）** | 会議を検知して聞き、録音を残さず文字起こしとRecapだけ返す | FR-MT群 | ✅ 要件は完備。コピーとの整合1点のみ（§2.6） |
| C7 | **Morning Brief + Evening Wrap** | 毎朝・**毎夜**、タスクの洗い出しと優先順位付けが済んでいる | FR-MB群（朝のみ） | ⚠️ 夜が無い → §2.7 新規FR-EB群 |

## 2. 機能別のギャップと新規FR草案

FR番号は既存の安定識別子規約に従い、新グループ（FR-AIS / FR-EB / FR-REF / FR-PAT）と既存グループへの追記で構成する。

### 2.1 C1: パッシブキャプチャ — 要件は充足。セキュリティ強化の取り込みのみ

キャプチャ本体はFR-CAP群で完備。監査（context-layer-audit §3）でv1確定した2点をNFRに昇格させる:

**NFR-SEC-06（MUST・新規）**: ローカルDBはSQLCipherで暗号化し、鍵はKeychainに保存する。既存平文DBからの移行マイグレーションと手順書を伴う。（監査決定 2026-07-25「DB暗号化はv1でやる」）

**NFR-SEC-07（MUST・新規）**: event log書き込み前に、secretパターン（`sk-` / `ghp_` / JWT / クレジットカード番号等）をマスクするリダクション段を通す。マスク規則はテスト可能なデータとして分離する。

> ~~競合文脈: Coast（画面録画＋ローカル推論）との対比で、「録らない・軽い・説明できる」はキャプチャ層の唯一の構造的優位。~~ **← 2026-07-30 オーナー提起により方針転換（§8）。差別化軸は「録らない」から「デバイスから出さない・期限つきで消える（ガバナンス）＋イベント駆動の軽さ」へ張り替える。**

### 2.2 C2: ワールドモデル — スレッドを要件に正式編入

実装先行している thread 構造（`thread_key` / `threads` テーブル / salience）に要件番号を与える:

**FR-MEM-40（MUST, Std・新規）**: event logの各行は `thread_key`（会話・スレッド識別子）を持ちうる。生成規則: Gmail=threadId / Slack=channel+thread_ts / GitHub=issue URL / AIセッション=session id / キャプチャ=アプリ＋正規化ウィンドウタイトル。マイグレーションはadditive。

**FR-MEM-41（MUST, Std・新規）**: `threads` テーブル（title / summary / participants / project_id / last_activity_at / **salience** / confidence）を第一級のstateとして持つ。summaryはDream Cycleが更新する。salienceは直近性・未処理度（open_loop有無）・現在画面との一致・語句一致の加重で算出し、純関数としてテスト可能にする。

**FR-MEM-42（MUST, Std・新規）**: Context Pack: チャット・ドラフト・Memory APIへ渡すコンテキストは、`assemble_context(query, budget)`（ハイブリッド検索＋state facts＋現在画面＋スレッド優先＋トークン予算）で組み立てる。confidenceゲート（FR-ST-20）を通過したもののみをモデルに渡す。p95はローカル検索SLO（500ms）内。

### 2.3 C3: ユニバーサル・コンテキスト配布（ShogunMCP）— 位置づけの昇格と配布経路の拡充

**現状の問題**: Memory API（FR-API群）は要件上「Proのおまけ」の位置にあるが、ポジショニング上は「全てのモデルでShogunMCPが使える」= **プロダクトの看板**である。Nessieが配布3経路（MCP + CLI + agent skill）を先に整えた今、配布面の完成度自体が競争軸になっている。

**FR-API-07（MUST・新規）**: 配布経路として既存のMCPサーバー / CLI / RESTに加え、**agent skill / セットアップレシピ**を提供する: 主要AIツール（Claude Code / Claude Desktop / Cursor / その他MCP対応クライアント）ごとに、ShogunMCPを1コマンド（または1操作）で登録できる導線を設定画面とCLI（`shogun mcp install <client>`）に用意する。生成される設定はローカルMCPエンドポイントを指すのみで、トークン以外の秘匿情報を含まない。

**FR-API-08（MUST・新規）**: `memory.get_context_pack` ツール: 外部AIがタスク文字列を渡すと、FR-MEM-42のContext Pack（根拠event id・confidence帯付き）を返す。「お気に入りのAIに構造化して渡す」の実体であり、UIのチャットとAPI経由で同一の組み立てロジックを使う（不変条件6）。

**FR-API-09（SHOULD・新規）**: 外部AIクライアントごとの利用状況（どのクライアントが・いつ・どのツールを呼んだか。内容は含まない）をFull UIで可視化する。コンテキスト配布が「効いている」ことをユーザーが確認できることが、スイッチングコスト形成の起点になる。

**プラン境界の変更提案（要オーナー判断 → §6-1）**: Memory APIの**読み取り系**（search / get_context / state照会 / get_context_pack）をStandardへ下げ、**書き込み・実行系**（append_note / propose_update / actions.execute）はPro維持とする。根拠: (a) 読み取り系はLLM呼び出しを伴わずBYOK不要のため、「プラン境界＝キー境界」（ADR-003）を破らない。(b) ADR-003の区分は「Standard=観測系 / Pro=実行系」であり、読み取りAPIは観測系に属する。(c) 「全てのAIで使えるコンテキストレイヤー」を看板にする以上、配布面が最上位プラン限定では体験の入口が塞がる。

### 2.4 C4: AIツール間コンテキスト統合 — 新規FR-AIS群

監査（context-layer-audit §5-2、スコープ確定 2026-07-25）でv1決定済み。要件として正式化する。

**FR-AIS-01（MUST, Std・新規）**: AIツールとのやりとりを新ソース `ai_session` としてevent logに取り込む。取り込み優先順位と方式:

| ツール | 方式 | 備考 |
|---|---|---|
| Claude Code | ローカルセッションファイル（`~/.claude/projects/**/*.jsonl`）の読み取り | 役割・時刻・セッションID構造化済み。最高精度 |
| Codex CLI等のローカルログを持つツール | 同様のローカルファイル読み取り（形式は個別調査） | — |
| ChatGPT / ブラウザ版チャット | AXキャプチャ＋会話セグメンタ（user/assistant境界の推定）、または公式エクスポートの手動取り込み | ローカル履歴が無いため |

**FR-AIS-02（MUST, Std・新規）**: 取り込みは**オプトイン**とし、ツール単位・プロジェクト/ディレクトリ単位の除外設定を必ず用意する。取り込み対象ファイルの読み取りはローカル処理のみで、egressを伴わない（トレーサビリティ対象外だが、取り込み状況は設定画面に表示する）。

**FR-AIS-03（MUST, Std・新規）**: `ai_session` イベントは `thread_key`=セッションIDを持ち、既存の検索・抽出・Fusion・state推定に**そのまま**乗る（専用経路を作らない。ソース対称の原則）。

**FR-AIS-04（MUST, Std・新規）**: AIセッション由来のstate候補（「Claudeでこう決めた」等）はprovenanceに `source=ai_session` を保持し、Recap/Brief/回答での根拠表示時に「AIツールでのやりとり由来」であることを区別可能にする。

> 位置づけ: これが「全てのモデル間のコンテキストを共有・統合できる」の取り込み側の半分であり、C3（配布側）と対になる。取り込み（C4）→ ワールドモデル（C2）→ 配布（C3）で、SHOGUNは**他のAIツールを置き換えずその下に座る**。

### 2.5 C5: ⌥ワンアクション実行 — 新規FR-NU-10

「Optionボタンを押すだけで実行」を要件化する。ただしOptionは修飾キーであり常用されるため、単押しトリガは誤発火リスクが高い。Phase 0のホバー誤発火検証と同じ規律で扱う:

**FR-NU-10（MUST, Std提示 / Pro実行・新規）**: ⌥（Option）キーの**ダブルタップ**（既定。単押し・長押しは誤発火検証の結果で選定）で、Context Fusionの最上位アクションを即時起動する:
- 最上位アクションがL1: 即実行し、Notchに事後表示
- L2: Notchが該当アクションを選択済み状態でExpandedし、Enter相当の1操作で確定
- L3: 通常のL3確認フロー（プレビュー必須）へ直行。**⌥経由でもL3の明示確認は省略しない**（不変条件4）
- 発火からNotch反応まではNotch展開SLO（100ms）に従う
- 設定で無効化・キー変更可。誤発火率の計測コードを同梱する（Phase 0の問い4と同型）

**FR-CF-06（SHOULD・新規）**: ⌥起動時のアクション確定履歴（どの候補が最上位で、採択されたか）をPatternsレイヤー（§2.9）の学習入力として記録する（ローカルのみ）。

### 2.6 C6: 会議ノート — 要件変更なし。コピー整合のみ

FR-MT群は完備。1点だけ、マーケコピー「高精度な**リアルタイム文字起こし**」とFR-MT-10（会議中はライブ文字起こしを**表示しない**）の見かけ上の緊張がある。

**判断（提案）**: 設計は変えない。文字起こし処理自体はリアルタイム（ストリーミングASR）であり、コピーは事実に反しない。ただし外部コピーは「リアルタイムに文字起こし、会議後に議事録」のように**表示タイミングを誤解させない**表現に寄せる。FR-MT-10の理由（流れる字は会議への集中を壊す）は堅持する。

### 2.7 C7: Evening Wrap — 新規FR-EB群

「毎朝、毎夜にタスクの洗い出し、優先順位付け」の**夜側**を新設する。Morning Brief（Dream Cycle成果物・Batch API・朝提示）と対になる、**終業時のローカル生成サマリ**:

**FR-EB-01（MUST, Std・新規）**: Evening Wrapは1日の終わり（既定17:00〜21:00の間の「作業終息」検知時、または設定時刻）に生成・提示する。内容:

| セクション | 内容 | 出典 |
|---|---|---|
| Today's outcome | 今日クローズしたcommitments / open_loops、実行したアクション数 | state tables / 実行履歴 |
| Still open | 今日動きがあったが未クローズの事項（優先順） | state tables |
| Tomorrow first | 明日期限のcommitments＋翌日の予定（先頭3件） | state tables / Calendar |
| Loose ends | 今日発生した未処理の新規open_loops | state tables |

**FR-EB-02（MUST, Std・新規）**: Evening Wrapは**ローカルデータのみで構成**する（LLM文章生成なし・egressなし）。Dream Cycleの前段に位置し、「夜のWrapで見た状態」が「翌朝のBriefで整理されて返ってくる」という1日のループを作る。優先順位付けはsalience / overdue / staleness の既存指標で行う。

**FR-EB-03（MUST, Std・新規）**: 提示は割り込まない原則に従う: 生成完了時にインジケータをゴールドにするのみで、自動ポップアップしない。既読管理はMorning Briefと同一。

> LLM整形を伴う「夜版Brief」をBatch APIで作る案は、Dream Cycleの実行時間帯（深夜）と重なり二重コストになるため採らない。夜はローカル集計、朝はBatch生成、で役割を分ける。

### 2.8 C8: 参照解決 — 新規FR-REF群

実装先行（`thread::is_referring` / `Db::resolve_referent`）に要件番号を与える:

**FR-REF-01（MUST, Pro・新規）**: チャット入力に指示詞（「あの件」「例の」「さっきの」等。言語別データとして管理）を検出したら、threadsのsalienceランキングで対象スレッドを解決する。候補が一意に絞れない場合は**推測で答えず**、上位2候補の二択で聞き返す。

**FR-REF-02（MUST, Pro・新規）**: 参照解決を経た回答は必ず根拠（provenance: どのメール/メッセージ/セッションか）を出典チップとして表示する。低confidenceの状態はFR-ST-20の規則どおり「〜の可能性」として渡す。

**FR-REF-03（MUST, Pro・新規）**: 参照解決はテキスト入力を正とし、音声入力は将来の前段追加とする（参照解決ロジックは音声/テキスト共通資産。監査決定 2026-07-25）。

### 2.9 C9: Patterns / Lessons — v1.5シードとして定義

ポジショニングの「使うほど賢くなる」（Layer 4/5、ワールドモデルの予測・因果次元）に要件上の名前を与える。**v1では基盤（データ収集）のみ、学習・適用はv1.5**:

**FR-PAT-01（MUST, Std・v1範囲）**: アクション提案の採択・修正・却下、⌥起動の確定履歴、Recap候補の`[Track]`/破棄を、学習入力イベントとしてローカルに記録する（`action_feedback` テーブル。additive）。**この記録はデバイス外に出さない。**

**FR-PAT-02（v1.5・予告）**: 記録した採択パターンから、(a) Fusionの優先度スコアの個人化、(b) ドラフトの口調・定型の学習、(c) 「この文脈ではいつもこうする」のL2提案化、を行う。設計はv1.5要件定義で行い、v1では実装しない。

> スコープ規律: FR-PAT-02をv1に前倒ししない（§3.2のスコープ表と同じ扱い）。ただしFR-PAT-01の記録を今から始めないと、v1.5時点で学習データがゼロになるため、**記録だけはv1に含める**。

## 8. 方針転換設計: 視覚キャプチャ（画像）と音声保存（2026-07-30 オーナー提起）

**オーナー提起の内容**: 精度を出すために画像を撮るべき。データ量削減とプライバシー配慮の仕組みを前提に、画像キャプチャを導入する。会議等の音声も取得（保存）してよい。

これは**CLAUDE.md絶対不変条件2（画像・音声データを一切保存しない）の改定を伴う**転換であり、Gmail/Composio決定（2026-07）と同じ「明示的・記録済みの決定」として扱う。本節はその設計と、確定に必要な残りの判断（OPEN-14〜17）を定義する。

### 8.1 変えるもの / 変えないもの（プライバシー線の張り替え）

| 項目 | 現行 | 転換後（提案） |
|---|---|---|
| 不変条件2 | 画像・音声を一切保存しない | **画像・音声を取得・ローカル保存できる**（条件は§8.2/8.3） |
| 不変条件3 | 生データはデバイス外に出さない | **変更しない。むしろ強化して明文化**: 画像・音声はいかなる経路でもデバイス外へ送信しない（クラウドVLM・クラウドASR禁止）。クラウドに出るのは従来どおり抽出テキストのチャンクのみ |
| ブランドの線 | 「録らない」 | 「**デバイスから出さない・期限つきで消える**」（ローカル処理・暗号化・保持期限・ワンタップ削除） |

録画常時型の競合に対する差別化は「録る/録らない」から「**ガバナンス**（何を・どれだけ・いつまで持つかをユーザーが制御でき、外に出ない）」へ移す。軽さ（イベント駆動・連続録画しない）は引き続き優位として維持する。

### 8.2 視覚キャプチャ — FR-VIS群（草案）

**FR-VIS-01（MUST）**: 視覚キャプチャはScreenCaptureKitによる**イベント駆動のキーフレーム取得**とし、連続録画（動画）は行わない。取得トリガ: フォーカス切替・有意な内容変化（AXテキスト差分・スクロール静止後）。perceptual hashで重複フレームを破棄する（データ量削減の第1段）。

**FR-VIS-02（MUST）**: 取得フレームは即時**オンデバイス処理**でテキスト・構造を抽出し（OCR: Vision framework。将来ローカルVLMの差し替え余地）、抽出結果は既存のevent log経路に乗せる（専用経路を作らない）。これによりAXの空白地帯（Electron・独自描画・図表・画像内テキスト）を埋める。**精度向上の主目的はここで達成される。**

**FR-VIS-03（MUST）**: フレーム保持は2モード: (a) 抽出後即破棄（テキストのみ残る） / (b) ダウンスケール・再圧縮したキーフレームを**暗号化して期間保持**（視覚リコール用。保持期限超過で自動削除）。既定モードと既定保持期間はOPEN-15で確定する。

**FR-VIS-04（MUST）**: 除外リスト（FR-CAP-05/06）・一時停止（FR-CAP-07）・SecureTextField除外は視覚キャプチャに**同一適用**する。除外対象がフォーカス中はフレーム取得自体を行わない。NFR-SEC-07のsecretリダクションは抽出テキストに適用し、保持フレーム側への領域マスクの実現可否はスパイクで検証する。

**FR-VIS-05（MUST）**: 画像はいかなる経路でもデバイス外へ送信しない。Batch API / BYOK / MCPへ送られるのは抽出テキストのチャンクのみ（不変条件3維持）。保持フレームはトレーサビリティの対象外（egressしないため）だが、ストレージ使用量を設定画面に表示する。

**FR-VIS-06（MUST）**: リソースは別枠予算で計測する: 視覚キャプチャ＋OCRのCPU・メモリ・ストレージ上限を定め、アイドルSLO（CPU 5%）と混ぜない。ストレージは上限到達で古い順に自動削除。バッテリー影響を計測しContext Healthに出す。

**FR-VIS-07（MUST）**: 権限とオンボーディング: 視覚キャプチャは**画面収録（Screen Recording）のTCC権限**を新たに要するため、オンボーディングで目的（何を抽出し、何が外に出ないか）を開示した上で要求する。拒否時はAXテキストのみの現行動作へグレースフルに縮退する（FR-CAP-08と同型）。

**検証ゲート（Phase 0と同型）**: 本実装前にスパイクで以下に答える: (1) イベント駆動取得＋OCRのCPU/バッテリー実測が予算内か (2) OCR追加でstate抽出精度が実際にどれだけ上がるか（評価セットで前後比較） (3) ストレージ増加率の実測。No-Goなら「(a) 抽出後即破棄モードのみで出荷」へ縮退する。

### 8.3 音声保存 — FR-MT群の改定（草案）

**FR-MT-12改定案**: RAMリングバッファ30秒制限を撤廃し、Recording中の音声を**ローカル暗号化ファイル**として保存できるようにする。transcript_segmentsと時刻リンクし、Recapから該当箇所を聞き直せる（検証可能性の向上）。ストリーミングASR制約も撤廃され、ファイルベースの高精度ASR・モデル改善時の再文字起こしが可能になる。

**保持規律（新設）**: 保持期間は既定値つき（OPEN-16で確定）・設定変更可・期限超過で自動削除・セッション単位の即時削除可。音声はいかなる経路でもデバイス外へ送信しない（クラウドASR禁止を維持）。

**変わらないもの**: 既定OFF＋オプトイン（FR-MT-01）、三段オフ（FR-MT-02）、Offeredの事前提示（FR-MT-08）、Recordingピル常時可視（FR-MT-09）、bot参加しない（Non Goal）。**「黙って録っていた」を構造的に作らない設計は全て維持する。**

**開示文言の改稿（FR-MT-03）**: 「この会議の音声はこのMacの中だけで処理・保存され、外部に送信されません。録音は{N日}で自動削除され、いつでも削除できます」— 事実と実装の一致テストも文言に合わせて更新する。

## 9. 会議ノートUX要件（新規ワークストリーム。2026-07-30 オーナー指示）

**指示内容**: 裏側の仕組みはあるが、リアルタイム翻訳・ノートとしての使いやすさ・先行ノートプロダクト水準のUIUXが未設計。設計が必要。

現行FR-MT群は仕組み（検知・ASR・Recap・state接地）が中心で、「ノートプロダクトとしての完成度」の要件がない。先行プロダクトが標準にした体験（雑メモ→AI清書のco-writing、テンプレート、ライブラリ、翻訳）を、SHOGUNの規律（割り込まない・根拠付き・state接地）の上に載せる。FR-MTUX群として草案化する:

### 9.1 サーフェス

**FR-MTUX-01（MUST, All）**: 会議ノート**専用ウィンドウ**: Recordingピルから1操作で開く。ユーザーメモ欄（常時編集可）＋静かなステータス行で構成。Notch Expandedの簡易メモ（FR-MT-10）はこのウィンドウの縮小ビューとする。

**FR-MTUX-02（MUST, All）**: Full UIに**会議ライブラリ**: 検索（既存FTS）、人物・プロジェクト別フィルタ、繰り返し会議のシリーズビュー（前回の決定・宿題を次回に引き継ぐ）、各会議のRecap / 文字起こし / ノート / （保存時）音声への導線。

### 9.2 co-writing（雑メモ→清書）

**FR-MTUX-03（MUST, All）**: 会議中のユーザーメモは断片で良い前提とし、会議後にAIが文字起こしと突合して**清書（enhance）**する。清書はユーザーのメモを**上書きせず**、原文＋清書版の2層で保存する（いつでも原文に戻れる）。清書はRecap生成（FR-MT-16、Select KK Batch）と同一ジョブで行う。

**FR-MTUX-04（SHOULD, All）**: 会議中、決定・宿題らしき発言を検知したら、ノート欄の**専用レーンに候補チップを静かに追加**する（ユーザーは無視・削除できる。音・ポップアップなし）。ライブ文字起こし全文表示とは別物であり、FR-MT-10の趣旨（流れる字で集中を壊さない）は維持する。

### 9.3 ライブ表示とリアルタイム翻訳

**FR-MTUX-05（MUST, All）**: FR-MT-10を改定し、ライブ文字起こしペインを**既定OFFのトグル**として提供する（既定挙動は現行どおり非表示。見たい人には見せる）。

**FR-MTUX-06（MUST, All）**: **リアルタイム翻訳**: ASRテキストを設定言語へストリーミング翻訳して表示するペインを提供する（多言語会議が主ユースケース）。翻訳方式はオンデバイスを第一候補とし（OPEN-18）、クラウド翻訳を使う場合もBYOKレーン・**テキストのみ**・トレーサビリティ必須（音声は出さない。§8.1の線と整合）。

### 9.4 テンプレート・会議後編集・エクスポート

**FR-MTUX-07（SHOULD, All）**: ノートテンプレート（1on1 / 商談 / スタンドアップ / インタビュー等）。予定タイトル・シリーズ履歴から自動で候補を当てる。

**FR-MTUX-08（MUST, All）**: Recapは**編集可能なドキュメント**として扱う（追記・修正可）。`[Track]`チップ（FR-MT-17）とWhy?根拠ジャンプ（FR-MT-18）は編集後も維持する。

**FR-MTUX-09（MUST, All）**: エクスポート: Markdownコピー / ローカルファイル書き出し = L2。外部サービスへの共有・送信はL3で、本ワークストリームの対象外（既存スコープ踏襲）。

### 9.5 要判断（**2026-07-30 提案どおり承認・FR-MTUX-06へ反映済み**）

| ID | 論点 | 選択肢 | 提案 |
|---|---|---|---|
| OPEN-18 | リアルタイム翻訳の方式 | オンデバイス翻訳モデル同梱 / macOS Translation framework / BYOKストリーミング翻訳（テキストのみ） | **Translation frameworkを第一候補にスパイク**（追加バイナリなし・オフライン対応）。品質不足ならBYOK翻訳をオプトインで併設 |
