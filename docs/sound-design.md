# 起動音・通知音の設計（Issue #49）

作成日: 2026-08-10 / 対象Issue: [#49 起動音や通知音の音の設計](https://github.com/Torutesu/ShogunAI-/issues/49)

> この文書は「どんな音にするか」より先に「**いつ黙るか**」を決める。SHOGUN はマイクとシステム音声を常時読める製品なので、UI が鳴らした音は自分の文字起こしと通話相手の耳に入りうる。音色の議論はその制約の後にしか意味を持たない。

## 0. 結論サマリ

| # | 決定 |
|---|---|
| D1 | **ログイン起動では鳴らさない。** 起動音はオンボーディング完了時の1回のみ（"Signature cue"）。以後は既定で無音 |
| D2 | **どこかのプロセスがマイクを掴んでいる間、SHOGUN は一切鳴らさない**（内蔵スピーカー出力時）。判定は既存の `mic::input_in_use()` を使う |
| D3 | 音を持つのは **Ack / Ready / Ask / Fail** の4カテゴリのみ。進捗・L1完了・情報提供には音を割り当てない |
| D4 | **L1（自動実行）は常に無音。** 音が鳴る＝ユーザーの操作か判断が関わっている、という対応を崩さない（不変条件4と対になる規律） |
| D5 | macOS の「サウンドエフェクトを再生」が OFF なら SHOGUN も全面無音。独自設定で上書きしない |
| D6 | 音は**常に冗長チャンネル**。音だけで伝わる情報を作らない（正はノッチの視覚状態） |
| D7 | Focus / おやすみモードは公開APIで読めない。**読もうとしない。** 観測可能な状態（マイク・会議・出力経路）とユーザー設定の静音時間帯で代替する |
| D8 | 設定は3段（Off / Essential / Full）。既定 **Essential**（= Ask と Fail のみ） |

## 2. SHOGUN 固有の問題 — 自分の音が自分の文字起こしと他人の耳に入る

UI 音が SHOGUN 自身の音声パイプラインへ戻る経路は3つある。1つは既に塞がっており、2つは開いている。

### 2.1 経路A: システムタップ（**安全。対処済み**）

`system_tap.rs:180` は `CATapDescription::initStereoGlobalTapButExcludeProcesses` を**自プロセス除外**で構成している（`//! ...a private, unmuted global CATapDescription that excludes our own process`）。したがって SHOGUN が鳴らした音がタップ経由で `Speaker::Other` として文字起こしに載ることはない。

これは追加対処不要だが、**将来この除外を外す変更をしてはならない**という制約が生まれる。本文書をその根拠として残す。

### 2.2 経路B: マイク（**開いている。危険**）

内蔵スピーカーから鳴らした音は、同じ筐体の内蔵マイクが拾う。会議レーンはマイク入力を `Speaker::Me` として Deepgram へ送るため、

- SHOGUN のチャイムが**自分の発話として文字起こしに混入**する（"ping" のような擬音、あるいは無意味なトークン）
- 混入したテキストは Recap・要約・state tables の根拠イベントにまで伝播する

タップ経路と違い、これは API で除外できない。**鳴らさないことでしか防げない。**

### 2.3 経路C: 通話相手の耳（**開いている。最も損失が大きい**）

会議アプリはマイク入力をそのまま相手へ送る。ヘッドホンを使っていない参加者が SHOGUN のチャイムを鳴らせば、**その音は会議の全員に聞こえる**。しかも相手には出所が分からない。

「作業フローを一切崩さない」ことを掲げる製品が、会議中に正体不明の音を撒くのは単純に致命的である。

### 2.4 すでに必要な信号は持っている

`apps/desktop/src-tauri/src/mic.rs:140` の `mic::input_in_use()` は「**いずれかの入力デバイスが、いずれかのプロセスに使われているか**」を返す。デフォルト入力だけでなく全入力デバイスを走査する実装で、会議検知が既にこれに依存している。

これは「今この瞬間、音を出したら誰かの通話に乗る可能性があるか」を判定する信号としてそのまま使える。**新規実装は不要で、既存関数を音の gate として読むだけでよい。**

## 3. 沈黙が既定（Silence-first）

音の設計とは、鳴らす音を選ぶことではなく、**鳴らさない条件を先に固定すること**である。4つの沈黙規則を置く。

| 規則 | 内容 | 理由 |
|---|---|---|
| **S1. Hot-mic silence** | `mic::input_in_use()` が true かつ出力が内蔵スピーカー → **全面無音**（Fail も含む） | §2.2 / §2.3。例外を作らない。会議中に音が要るなら視覚で伝える |
| **S2. Unattended silence** | ユーザー操作を起点としないイベントは、Ask と Fail 以外すべて無音 | 背景で走るものが鳴きだすと、常駐アプリは1週間で嫌われる |
| **S3. L1 silence** | L1（自動実行）は結果に関わらず常に無音 | 不変条件4と対。「音がした＝人が関与している」対応を保つ |
| **S4. Quiet hours** | ユーザー設定の静音時間帯（既定 22:00–08:00）は Ask / Fail も無音 | Dream Cycle は夜間に走る。寝ている Mac は鳴らない |

鳴らしてよい条件は、この否定形として一意に決まる。

```rust
// 疑似コード。実体は shogun-core 側の純関数（テスト可能）に置く。
fn should_play(cue: Cue, env: &SoundEnv) -> bool {
    if !env.os_ui_sounds_enabled { return false; }          // D5
    if env.pref == SoundPref::Off { return false; }
    if env.quiet_hours_now { return false; }                 // S4
    if env.mic_in_use && env.output_is_builtin_speaker { return false; } // S1
    match cue.category {
        Category::Ask | Category::Fail => true,              // Essential
        Category::Ack | Category::Ready => env.pref == SoundPref::Full, // S2
    }
}
```

`SoundEnv` はキャッシュ済みの値で構成し、**再生要求のたびに Core Audio へ問い合わせない**（§8.5）。

## 4. 音を持つのは4カテゴリだけ

| カテゴリ | 意味 | ユーザーにとっての問い | 既定 |
|---|---|---|---|
| **Ack** | あなたの操作を受け取った | 「押せた?」 | Full のみ |
| **Ready** | あなたが待っていたものが用意できた | 「まだ?」 | Full のみ |
| **Ask** | あなたの判断が要る（L3） | 「私の承認待ちのものはある?」 | **Essential（既定ON）** |
| **Fail** | 放置するとあなたの作業が失われる | 「壊れてない?」 | **Essential（既定ON）** |

### 音を割り当てない3つのアンチカテゴリ

- **進捗**（同期中・インデックス中・文字起こし中）: 終わりが未定のものに音を付けると、音が環境音になる
- **L1 の完了**: 自動実行が成功したことは、そもそもユーザーの注意を要求しない（要求するなら L1 に置いた設計が間違っている）
- **情報の到着**（Morning Brief の生成完了など）: 読む時刻はユーザーが決める。到着時刻に鳴らす理由がない

## 6. 起動音の設計

### 6.1 なぜログイン起動で鳴らさないか

- SHOGUN はログイン項目として常駐する（`launch_at_login.rs`）。起動は**ユーザーが意図した瞬間ではない**。ユーザーはログインしたのであって、SHOGUN を起動したのではない
- 毎朝同じ音が鳴るものは、3日で無視され、1週間で設定から切られる。「起動音」を作って最初にオフにされるのは、音の資産としてもブランドとしても損
- 起動直後は AX 権限確認・DB オープン・キャプチャ開始が同時に走る最も重い区間で、そこにオーディオデバイスの wake を足したくない（SLO: アイドルCPU 5%）

### 6.2 では起動音はどこにあるか — Signature cue

**オンボーディング完了時に、生涯1回だけ鳴らす。** ここは、

- ユーザーが明示的に操作を完了させた瞬間である（Ack の最も強い形）
- 権限付与を終え「SHOGUN が動き出す」ことが体験として意味を持つ唯一の点
- 1回しか鳴らないので、少し長く（〜600ms）、印象に残る音を許容できる

設定に `Play the startup sound`（既定 **OFF**）を置き、明示的に望むユーザーだけが毎回の起動で聞けるようにする。既定を OFF にする以上、この設定は「隠し機能」に近い扱いでよい。

## 7. 音そのものの設計

### 7.1 モチーフ

**二音と、その間の「間」。** SHOGUN のマークは折り紙の兜（一枚の紙を折って形が立ち上がる）である。音もこれに合わせ、単発の電子音ではなく「一つの素材が二度鳴る」構成にする。

| Cue | 音型 | 長さ | 備考 |
|---|---|---|---|
| Ack (start) | 上行短3度（例: A5 → C6） | 90ms | 「開いた」 |
| Ack (end) | 下行短3度（C6 → A5） | 110ms | start の反転。対であることが聞いて分かる |
| Ready | 上行完全5度、2音目を長めに減衰 | 220ms | 「用意できた」 |
| **Ask** | 同音を2回（間 120ms） | 260ms | 反復＝返事待ち。音高を動かさないので急かさない |
| **Fail** | 下行長2度、倍音を濁らせない | 180ms | 警告音にしない。作業を中断させない規約（CLAUDE.md）に合わせ、驚かせずに気づかせる |
| Signature | Ready の拡張（3音、最後に長い減衰） | 〜600ms | 生涯1回 |

全 cue は**同一音源から派生**させる（木・紙・柔らかい金属の減衰音のいずれか1つを選び、ピッチと包絡だけを変える）。これで「家族」に聞こえる。

### 7.2 音響仕様（実装が守る数値）

| 項目 | 値 | 理由 |
|---|---|---|
| ラウドネス | **-26 dB**（K特性平均。下記注）、sample peak ≤ -3 dBFS | システム音量が中程度の時に「聞こえるが驚かない」帯。6ファイルとも同じ手続きで正規化するので cue 間の差は生じない |
| 主要帯域 | 1.5–4 kHz に重心 | MacBook 内蔵スピーカーで痩せない帯域。低域は再生されずラウドネスだけ食う |
| Attack | ≥ 3ms | クリックノイズ回避 |
| Release | ≥ 40ms のフェードアウト、無音で終端 | 途中で切れた音は故障に聞こえる |
| フォーマット | 48kHz / 16bit / mono / AIFF or WAV（非圧縮） | デコード遅延ゼロ。ファイルは各数十KB で、バンドルサイズ上の問題にならない |
| ファイル数 | 6（上表の cue 数） | 増やさない。増えた分だけ設計が薄まる |

**ラウドネスの測り方（注）**: BS.1770 の *統合* ラウドネス（400ms ブロックのゲーティング）は、100〜600ms しかない音には定義上そのまま当てはまらない。そこで K特性フィルタ（BS.1770-4 の pre-filter + RLB）を通した平均二乗を、cue 全体（400ms 未満は 400ms までゼロ詰め）で1回測る。**これは LUFS を名乗れる値ではない**ので、本書ではそう呼ばない。真の true-peak と実機での体感音量は §10 で別途確認する。

**実測値（`scripts/generate-cue-sounds.py` 出力）**: 6ファイルとも -26.00 dB、sample peak は -14.1〜-10.5 dBFS、クリッピングなし、全ファイルが無音で開始・終端。合計 158KB。

### 7.3 やらないこと

- **和の記号を音で説明しない**（銅鑼・尺八・鹿威し・和太鼓）。ブランド規約はクリシェを避ける方針であり、音でだけ例外にする理由がない
- 声・言葉・擬人化された効果音
- 出所不明のフリー素材。**自作、または CC0 / 買い切りライセンスのみ**を使い、由来と license を記録する（配布バイナリに載る資産である）

**実装での選択**: サンプリング素材を使わず、**スクリプトで合成**した（`scripts/generate-cue-sounds.py`）。自由端棒の固有モード（1 : 2.76 : 5.40）を1つの音源として全 cue を派生させ、ピッチ運動と包絡だけを変える。第三者素材が無いので追うべきライセンスも無い。音を変えたい時は WAV を直接編集せず、スクリプトを直して再生成する。由来は `apps/desktop/src-tauri/sounds/README.md` にある。

## 8. macOS 実装

### 8.1 API 選定

| API | 音量の従属先 | 遅延 | 判断 |
|---|---|---|---|
| `NSSound` | 通常出力・アプリ音量 | ファイル読み込みを伴うと数十ms（**メモリから構築すれば不要**） | **採用**（実装時に変更） |
| `AVAudioPlayer` | 通常出力・アプリ音量 | プリロードすれば ~即時（`prepareToPlay`） | 不採用（実装時に変更） |
| `AudioServicesPlaySystemSound` | システムアラート音量 | 低 | 不採用（アラート音量に乗ると音量制御をユーザーから奪う。**要実機確認**の挙動差もある） |

**採用（実装時の変更 / 2026-08-11）**: 初版は `AVAudioPlayer` を採用としていたが、実装では **`NSSound`** にした。理由は3つ:

1. `NSSound` は AppKit にあり、この shell は既に AppKit をリンクしている（AVFoundation の新規リンクが不要）
2. 起動時に `NSSound initWithData:` で6つのインスタンスを作って保持するため、`AVAudioPlayer` の `prepareToPlay` が解く「再生時のデコード遅延」は同じく解けている（プリロードの利得はAPI固有ではない）
3. `objc2-app-kit` は既に依存にあり、追加は feature 1つ（`NSSound`）で済む

`AVAudioPlayer` に戻す動機が出るとすれば、cue の同時再生・音量の個別制御・再生完了コールバックが必要になった時。現状どれも要らない。

**音源はバンドルリソースではなくバイナリに埋め込む（`include_bytes!`）。** 6ファイル計158KB。リソースにすると dev / bundle でパス解決が分岐し、「読み込み失敗で無音」と「ポリシーが無音を選んだ」が現象として区別できなくなる。埋め込みはこのクラスのバグを丸ごと消す。

### 8.2 OS 設定の尊重（D5）

システム設定 > サウンドの「サウンドエフェクトを再生」は `com.apple.sound.uiaudio.enabled`（`NSUserDefaults`, グローバルドメイン）で読める。**OFF なら SHOGUN の cue も全部止める。** 独自トグルで上書きできるようにはしない（OS 設定を無視するアプリになる）。

### 8.3 出力経路の判定（S1 の条件）

デフォルト出力デバイスの `kAudioDevicePropertyTransportType` を読み、`kAudioDeviceTransportTypeBuiltIn` なら「内蔵スピーカー」と判定する。`mic.rs` の `read_u32(device, ...)` と同型のコードで書ける（**新規の依存は不要**）。

- 内蔵スピーカー ＋ マイク使用中 → 無音（S1）
- ヘッドホン / BT ヘッドセット ＋ マイク使用中 → **鳴らしてよい**（相手には聞こえず、内蔵マイクへの回り込みもない）
- 判定失敗時は **内蔵スピーカーとみなす**（安全側。`mic.rs` の「失敗は false」と同じ思想で、より損失の小さい側へ倒す）

### 8.4 Focus / おやすみモードを読まない理由（D7）

Focus の状態を読む公開 API は無く、`~/Library/DoNotDisturb/DB/` を覗く手は署名済み配布と TCC の下で壊れやすく、規約上も勧められない。**読もうとしない。** 代わりに §3 の観測可能な状態（マイク・出力経路・時刻）で代替する。これは機能の劣化ではなく、壊れない設計の選択である。

### 8.5 SLO とリソース

- **展開 100ms に音のコストを載せない。** デコード済みバッファを常駐させ、再生要求は `play()` のみ。プリロードは setup 時に行う
- **音のためにオーディオデバイスを開きっぱなしにしない。** `NSSound` は停止中に出力デバイスを保持しない想定だが、これは**実機で確認する項目**（§10 A7）
- **環境の読み取りは cue ごとに実測する（実装時の変更 / 2026-08-11）。** 初版は「監視ループでキャッシュし、再生パスで Core Audio を叩かない」としていたが、実装では毎回読む。理由: S1 の判定材料であるマイク状態は**キャッシュが1秒古いだけで意味を失う**（会議が始まった直後こそが事故の瞬間）。コストは Core Audio のプロパティ読み取り3回で、しかもこのパスは同一音につき2秒に1回までしか走らない（下記スロットル）。正しさを取った
- **同一音のスロットル（初版に無かった追加）**: 同じ音は 2秒（`sound::MIN_GAP_MS`）以内に鳴らさない。承認が3件同時に積まれても、人間にとっては1つの出来事である。cue 単位ではなく**アセット単位**で数える（耳には同じ音だから）
- `SoundEnv` の各値（OS設定・出力経路・マイク使用中）は既存の監視ループでキャッシュ更新し、再生パスで Core Audio を叩かない

### 8.6 不変条件2 との関係（誤解防止）

不変条件2「音声データを一切保存しない」は**ユーザー由来の音声**（マイク・会議・システム音声）を対象とする。**アプリバンドルに同梱する cue 音源はこれに当たらない。** 将来のレビューで混同されないよう、ここに明記しておく。cue 音源は書き出しも録音もせず、読み取り専用で再生されるだけである。

## 9. 設定とアクセシビリティ

### 設定（Full UI > Preferences）

```
Sounds
  ( ) Off                — 何も鳴らさない
  (•) Essential          — 判断が要る時と、失敗した時だけ（既定）
  ( ) Full               — 操作の受領・完了も鳴らす
  [ ] Play the startup sound            （既定 OFF）
  Quiet hours  [22:00] – [08:00]        （既定 ON）
  [ Preview ]
  ⓘ Sounds are always muted while any app is using the microphone.
```

- 最後の1行は**必ず出す**。会議中に鳴らないのは不具合ではなく設計だと分かるようにする（サポート問い合わせを未然に消す）
- **Preview は好みの層（Off/Essential/Full）と quiet hours を無視して鳴らす**（ユーザーがボタンを押した以上、それは要求である）。ただし S1 と OS 設定には従う——それらは好みではなく他人と OS の話だから。マイクが理由で鳴らなかった時はその旨を返す
- 文言は英語・i18n-ready（v1規約）

### アクセシビリティ

- **音は常に冗長**（D6）。難聴のユーザーが音のみで失われる情報を作らない。すべての cue に対応する視覚状態（ノッチのインジケータ色・パネル表示）が先に存在すること
- 逆向きも成立させる: 視覚に頼れないユーザーにとって、Ask / Fail の音はノッチ（極小の視覚領域）を補う唯一の通知になりうる。**だから Essential の既定を ON にする**
- VoiceOver 使用時は VoiceOver 自身の発話と衝突しうるため、Ack/Ready を自動的に抑制することを検討する（**未決**、§12）

- **VoiceOver 併用時の抑制**: 併用実機での衝突具合が未確認
- **音源の制作方法**: 合成で確定（§7.3）。残る判断は「これで出荷するか、Signature cue だけプロに作らせるか」。実機で聴いてから決める
- **PTT の既定**: PTT は「押した実感」が体験の質に直結するため、Ack だけ Essential に含める例外を作るべきか。現状は含めない（＝ Full を選んだ人だけが聞く）
- `AudioServicesPlaySystemSound` の音量従属先の実機確認（§8.1 の表の「要実機確認」）

### 実装して分かったこと（2026-08-11 追記）

- **PTT の cue はマイクの開閉を挟む位置に置く必要がある。** 開始音を `voice_lane::start` の**前**に、終了音を `voice_lane::stop` の**後**に鳴らす。こうすると SHOGUN 自身の録音は自分の cue を絶対に拾わない（まだ／もう開いていないため）。会議録音中は PTT 自体が禁止されている（`voice_session.rs`）ので、残るリスクは「他アプリの通話が進行中」だけになり、それは S1 が捕まえる。**この順序が守られていれば、§12 の「PTT の Ack を Essential にするか」は S1 と衝突しない論点になる**（会議中の無音は S1 ではなく PTT 自体の禁止によるもの）
- **スロットルは cue 単位ではなくアセット単位。** 承認と会議 Offered は同じ `ask` を鳴らすので、耳の側で数えるのが正しい
- **失敗時の既定値は常に「静かな側」ではない。** 時刻取得に失敗したら正午とみなす（＝ quiet hours に入らない）ようにした。ここだけは逆で、「分からないから黙る」が Fail cue を殺すため。出力経路・OS設定・設定ファイルは従来どおり静かな側に倒す
