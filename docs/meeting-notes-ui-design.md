# 会議ノート — 音声レーンと UI 設計

会議を検知して開始し、終わるまで録り続け、終わったら**そのまま仕事になる**ノートを返す。
本書はその UI とデータ経路の設計。

- 作成日: 2026-07-25
- 前提文書: `docs/meeting-context-and-dashboard-design.md`（会議コンテキストの器 = `session` / `calendar_occurrences`）
- 上位文書: `docs/requirements-v1.0.md` / `CLAUDE.md`

---

## 0. 決定事項（前回の未決を確定）

| 論点 | 決定 |
|---|---|
| 画面・会議の**録画** | **恒久的に不採用**。不変条件2はプロダクトの差別化そのもの。回避策も設計しない |
| **音声** | **やる**。ただし「録音を残す」のではなく「**聞いて、テキストだけ残す**」。音声はディスクに書かない |
| 開始 | **自動検知で開始**。ただし常に可視で、常に1タップで止まる（§3） |
| 会議中の UI | 自分のノートを打つ場所。**ライブ文字起こしは表示しない**（気が散る） |
| 終了後 | Recap = 要約＋決定事項＋約束の候補。**1タップで state に確定** |

この決定に伴い、**不変条件と要件の改訂が必要**（§1）。改訂せずに実装に入らないこと。

## 2. 音声パイプライン（何が RAM に留まり、何が残るか）

```
 マイク ────┐
            ├─→ [RAM リングバッファ 30s] ─→ オンデバイスASR ─→ transcript_segments（テキスト）
 システム音声┘        ↑ ここから先に音声は行かない          └→ session に紐づく
 (Core Audio tap)     └─ 破棄（ディスクにも、クラウドにも書かない）
```

- **リングバッファは 30 秒**。ASR が追いつかない場合は**古い音声から捨てる**（貯めない）。
  貯めれば「実質的な録音」になるので、上限は設計上の防壁として固定値で持つ。
- **文字起こしテキストは Warm 層**に入り、既存の検索・抽出・Fusion がそのまま効く。
- **クラウドに音声は出さない。** Recap の要約は既存の鍵レーン規律どおり
  **Select KK（Batch）** で、送るのは**文字起こしから作った処理用チャンク**のみ。トレース必須。
- speaker 分離は v1 では「自分 / それ以外」の2値まで（マイク入力か system 出力かで判別できる）。
  話者ラベルの精度は Recap の採用率で測る（`docs/meeting-context-and-dashboard-design.md` §3.5）。

### 2.1 スキーマ（additive）

```sql
CREATE TABLE transcript_segments (
  id INTEGER PRIMARY KEY,
  session_id INTEGER NOT NULL REFERENCES sessions(id),
  ts INTEGER NOT NULL,               -- epoch ms（セグメント開始）
  speaker TEXT,                      -- 'me' | 'other' | NULL（不明を NULL で持つ。推測で埋めない）
  text TEXT NOT NULL,
  origin TEXT NOT NULL,              -- 'asr' | 'caption'（キャプション由来かを provenance に残す）
  confidence REAL NOT NULL CHECK (confidence >= 0.0 AND confidence <= 1.0),
  created_at INTEGER NOT NULL
) STRICT;
CREATE INDEX idx_transcript_session ON transcript_segments (session_id, ts);

CREATE TABLE session_notes (            -- ユーザーが会議中に打った自分のノート
  id INTEGER PRIMARY KEY,
  session_id INTEGER NOT NULL REFERENCES sessions(id),
  body TEXT NOT NULL,
  updated_at INTEGER NOT NULL
) STRICT;
```

`origin` を持つのは、**キャプション由来か音声由来かで同意の要件が変わる**ため（§5）。

## 3. ライフサイクルと UI

### 3.1 状態遷移

```
  Idle
   │  会議検知（予定 / 会議アプリ前面 / マイク使用中 / 会議UIの痕跡）
   ▼
  Offered ──"Not now"──────────────────────────────────┐
   │  10秒のグレース（何もしなければ開始）              │
   ▼                                                   │
  Recording ──"Stop"──→ Wrapping ──→ Recap ──確定──→ state tables
   │                                                   │
   └─ 会議アプリ終了 / 予定終了 / 無音15分 → Wrapping   │
                                                       ▼
                                                     Idle
```

**Offered の 10 秒グレースがこの設計の肝。** 自動で始まるが、始まる前に必ず一度姿を見せ、
拒否が常に1タップで届く。「知らないうちに録られていた」を構造的に作らない。

### 3.2 Notch — Recording ピル（常時可視）

```
 ┌─────────────────────────────────────────┐
 │ ● Notes · 12:04   Weekly sync      ■ Stop│   ← 折りたたみ時のピル
 └─────────────────────────────────────────┘
   │        │          │                  └ 1タップで停止（確認ダイアログなし）
   │        │          └ 予定名（無ければアプリ名）
   │        └ 経過時間（"録り続けている"ことが一目で分かる）
   └ ライブドット（--live 緑。赤の録画ランプは使わない＝録画ではないから）
```

- **経過時間を必ず出す。** 状態のトグルだけだと「まだ動いているのか」が分からない。
- 停止は**確認なしで即停止**。止めることに摩擦を作らない（開始に摩擦がない設計とセット）。
- フルスクリーン中も Hidden にしない**唯一の例外**がこのピル（常時可視の要請が優先）。

### 3.3 Notch — Offered（検知直後の 10 秒）

```
 ┌─────────────────────────────────────────┐
 │ Weekly sync starting — taking notes in 8s│
 │                    [ Not now ]  [ Start ]│
 └─────────────────────────────────────────┘
```

- カウントダウンを見せる。無視すれば始まる。**"Not now" はこの会議だけ**（設定は変えない）。
- 長押し / 副操作で「このアプリでは今後録らない」に到達できる（§4 の三段オフの (b)）。

### 3.4 展開パネル — 会議中は「ノートを打つ場所」

```
 ┌──────────────────────────────────────────────────────┐
 │ ● Notes · 12:04  Weekly sync                  ■ Stop │
 ├──────────────────────────────────────────────────────┤
 │                                                      │
 │   Type your notes…                                   │  ← 自分のノート（唯一の主役）
 │   - pricing decision pending                         │
 │   - Alice takes the vendor thread                    │
 │                                                      │
 ├──────────────────────────────────────────────────────┤
 │ Listening · 3 participants          Not now  ⌄       │  ← 静かな1行。文字起こしは出さない
 └──────────────────────────────────────────────────────┘
```

**ライブ文字起こしを出さない**のは意図的な設計判断:

1. 流れる字を目で追うと会議に集中できない（ノートを取る道具としては逆効果）
2. ASR の誤りがその場で見えると、ユーザーは訂正したくなる。**訂正させる仕事を増やしてはいけない**
3. 誤りは Recap の段階で「文脈込みのモデル」が直せる — その前に人間に見せる必要がない

代わりに **"Listening" の一行**だけを出す。動いていることは分かり、内容は追わせない。

> ノートは「打っても打たなくてもよい」。打てば Recap がそれを軸に組み立て、打たなければ
> 文字起こしだけで組み立てる。**打つことを前提にしない**（会議中に打てない人の方が多い）。

### 3.5 Recap（終了直後）

```
 ┌──────────────────────────────────────────────────────┐
 │ Weekly sync · 32 min · 4 people                      │
 ├──────────────────────────────────────────────────────┤
 │ Summary                                              │
 │  Vendor renewal is settled at 12k for the year.      │
 │  Launch date moved to the 14th.                      │
 │                                                      │
 │ Decisions                                            │
 │  · Renewal at 12k — agreed                           │
 │                                                      │
 │ Picked up                          ← 候補。確定は1タップ│
 │  ✓ You: send the revised deck            [Track]     │
 │  ✓ Alice: owns the vendor thread         [Track]     │
 │  possibly: launch review on the 14th     [Track]     │
 │                                                      │
 │ Your notes                          [ Open ]         │
 ├──────────────────────────────────────────────────────┤
 │ From this meeting's transcript · 41 segments   Why? ⌄ │
 └──────────────────────────────────────────────────────┘
```

- **候補は候補として出す。** 低確度は `possibly:` 帯のまま（`confidence.rs` の既存ゲート）。
- `[Track]` を押した瞬間だけ confidence 1.0 + provenance=ユーザー編集で state に入る
  （要件 §6.4「ユーザー明示編集」経路）。これが**唯一の正直な昇格**。
- `Why?` で根拠セグメントに降りられる（provenance の可視化）。
- 外部への共有・送信は v1 に含めない（議事録の配布は L3 かつスコープ外）。

### 3.6 会議が終わったのに気づけなかった時

無音 15 分 / 会議アプリ終了 / 予定の終了時刻 +10 分 のいずれかで **自動 Wrapping**。
「止め忘れて延々と録り続けていた」を作らない。これも録音ではなく**注意の設計**の問題。

## 4. オフの設計（三段）

ユーザーが明示的に求めた点。**止め方は常に3つの粒度で存在する。**

| 段 | どこから | 効果 |
|---|---|---|
| (a) **全体オフ** | 設定 → Meeting notes → Off | 検知も ASR も走らない。マイクにも触らない |
| (b) **このアプリでは録らない** | Offered の副操作 / 設定の除外リスト | 指定した会議アプリでは提案しない |
| (c) **この会議は録らない** | Offered の "Not now" / Recording の "Stop" | 今回だけ。設定は変えない |

加えて:

- **既定は？** — 初回は **(a) Off**。オンボーディングで一度だけ説明して選ばせる。
  録音は「黙って有効になっていた」が最も許されない機能なので、ここだけはオプトイン。
- 設定に **除外リスト**（アプリ単位）と、**特定の予定を常に除外**（1on1 など）を持つ。
- 全体オフ中は、Notch にもピルを出さない（"オフなのに何か出ている" を作らない）。

## 5. 同意と法務（v1 に前倒しした以上、必須）

1. **開示テキスト**を Recap と設定に常設: 「この会議の音声はこの Mac の中だけで処理され、
   録音は保存されません。残るのは文字起こしテキストです」— 事実そのままなので強い。
2. **法域による既定の差**: 全当事者同意が要る地域がある。v1 は
   「**既定オフ＋明示オプトイン＋常時可視のピル**」で一律に運用し、地域別分岐は持たない
   （持つと必ず間違える）。
3. **provenance に origin を残す**（`asr` / `caption`）。「キャプションを読んだだけ」と
   「音声を聞いた」は説明責任が違う。
4. 参加者への告知は**プロダクトが代行しない**（会議に自動でメッセージを投げない）。
   ユーザーが自分の言葉で言うためのコピーを設定に置くに留める。

## 6. リソースと SLO

| 項目 | 予算 | 備考 |
|---|---|---|
| アイドル CPU | 5%（既存 SLO-06） | **会議中は別枠**。ASR 稼働中は 15% を上限に別途計測する |
| メモリ | リングバッファ 30s + ASR モデル | 3層メモリの Hot 上限（200MB）とは別勘定 |
| Recap 生成 | 会議終了から 60s 以内に初回表示 | 間に合わない場合は「文字起こしのみの縮退 Recap」を先に出す（空にしない） |
| バッテリー | 会議中の消費を計測し Context Health に出す | 「会議のたびに電池が溶ける」は使われなくなる直接原因 |

**会議中の CPU を既存 SLO と混ぜない。** 混ぜると「アイドル 5%」が意味を失う。

## 7. 実装順

| 段 | 内容 | 依存 |
|---|---|---|
| **M1** | `sessions` + 検知 + Notch の Offered/Recording ピル（**ASR 無しで**動かす） | 前設計の E4/E5 |
| **M2** | 会議中ノート（`session_notes`）+ 終了検知 + 縮退 Recap（ノートと予定だけ） | M1 |
| **M3** | オンデバイス ASR + `transcript_segments` + リングバッファの上限 | M2 + モデル選定 |
| **M4** | Recap 本体（Batch 要約 + 候補抽出 + `[Track]` 確定） | M3 + Batch 鍵 |
| **M5** | 三段オフ・除外リスト・オンボーディングのオプトイン | M1 と並行可 |

**M1/M2 は音声なしで出荷できる。** 検知と器と UI が先に立ち上がっていれば、ASR は
「解像度を上げる差し替え」で済む。逆順にしない。

> 採番注記: 要件書 §5.6 では Phase 1 の M1〜M5 と衝突するため、本書の M1〜M5 を
> **MT1〜MT5** と呼び分けている。以下の進捗も MT 表記に従う。

| 段 | 状態 | 実装 |

**MT5 の残り（オンボーディング）について**: アプリに FR-OB-01 のオンボーディング画面が
**そもそも実装されていない**（Phase 0 スパイクのため）。現状のオプトイン経路は設定画面の
トグルのみで、FR-MT-01 の実質（既定OFF・明示的な有効化・開示テキストの常設）は満たしているが、
「初回に一度だけ説明して選ばせる」導線は**オンボーディング画面の実装が前提**であり、
会議ノート単独では閉じられない。FR-OB-01/06 の実装時に併せて行う。

**未検証**: 実機（macOS + 実際の Zoom / Google Meet）でのピル表示・検知動作は未確認。
ビルドとテストは通っているが、`frontmostApplication()` 経由の検知が実環境で意図どおり
発火するかは実機確認が要る。

## 8. 未決事項

1. **ASR モデルの選定** — オンデバイス・ストリーミング・多言語（英語主・日本語併走の方針は
