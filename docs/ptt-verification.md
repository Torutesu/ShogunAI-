# Push-to-talk 実機検証チェックリスト（Issue #44）

このドキュメントは、**ユニットテストでは到達できなかった claim だけ**を集めたものです。
状態機械・SSE デコーダ・BufferSink・プロンプト組み立ては純粋なロジックなので `cargo test`
で守られていますが、ここに並ぶのは次のいずれかで、実機でしか確かめられません:

- **macOS の実際のイベント**を読む（`NSEvent` の device-dependent 修飾キービット）
- **AppKit の window server**の実挙動（`float_on_all_spaces` が別 Space / フルスクリーンに乗るか）
- **物理デバイス**（マイク・スピーカー・権限ダイアログ）
- **ネットワークと実 API キー**（BYOK 拒否、オフライン）
- **SLO の実測値**（初トークンまでの実時間）

各項目には「何をするか」「どうなれば OK か」を書き、**外したときに何が壊れているか**が
分かるものにはそれも書いてあります。結果欄は空にしてあります — 実行しながら埋めてください。

前提:
- ビルド: `cargo tauri dev`（または `cargo run -p shogun-desktop-spike`）でアプリを起動できること
- バンドル識別子は `dev.shogun.spike`（`tauri.conf.json`）
- 既定の長押しキーは**右⌘**（`hold_monitor.rs` の `HoldKey::RightCommand`）

## 1. Device-dependent 修飾キービット（右⌘ と左⌘ の判別）

`hold_monitor.rs` は「右⌘が物理的に押されているか」を、汎用の `NSEventModifierFlagCommand`
（`1<<20`）ではなく **device-dependent マスク `NX_DEVICERCMDKEYMASK`（`0x10`）** で判定します。
左⌘と右⌘は汎用ビットを共有するため、汎用ビットで見ると「左⌘を握ったまま右⌘を離しても
まだ押されている」と誤読し、離したことに気づけません（＝マイクが開いたまま残る）。
これはハードウェアが実際に送るビットに依存するので、実機でしか確認できません。

手順:

- [ ] ターミナルから `SHOGUN_PTT_DEBUG=1 cargo tauri dev`（または同env付きでバイナリを実行）で起動する
- [ ] **左⌘を押したまま**にする
- [ ] 左⌘を押したまま、**右⌘を押して、離す**
- [ ] ターミナルの `[ptt] flagsChanged code=… flags=…` の行を読む

期待する結果:

- [ ] 右⌘を**押した**行で `flags` に `0x10` のビットが立つ（例: `flags=0x00100010` のように `0x…10`）
- [ ] 右⌘を**離した**行で、左⌘をまだ握っているのに `0x10` が**消える**
      （`flags` の下位が `0x…08` などになり、`0x10` が落ちている）

**外したときの意味:** 離しても `0x10` が消えない、あるいはそもそも立たないなら、
`down_flag()` が読んでいるビットが実機のビットと合っていません。この場合 hold 検知全体が
間違っており、右⌘を離してもマイクが閉じない（開きっぱなしになる）恐れがあります。
`hold_monitor.rs:61` の `down_flag()` を疑ってください。

結果:

```
（flagsChanged のログをここに貼る）
```

## 2. 5つの hold シーケンス（＋放置による自動クローズ）

以下は**シミュレータ相手に手でトレースしただけ**で、実機では走らせていません。
各シーケンスは「開始1回・終了1回ちょうど」か「どちらも0回」でなければなりません。
録音の開始/終了は音（開始=Tink、終了=Pop）とパネルの出現/消滅で観測できます。
`SHOGUN_PTT_DEBUG=1` を立てておくと `[ptt] → recording` / `[ptt] → …` の遷移ログでも追えます。

> 判定のこつ: 「開始した」＝開始音が鳴りパネルが出る。「終了した」＝終了音が鳴りパネルが
> Transcribing に変わる（十分な長さを話した場合）。**300ms 未満の hold は誤爆として黙って
> 消える**（`min_hold_ms`）ので、各シーケンスでキーを押している間は必ず一言話してください。

- [ ] **(a) 左⌘↓ → 左⌘↑ → 右⌘↓（話す）→ 右⌘↑**
      → 最後の右⌘の hold が正しく動く（開始→終了が1回）。
      **これは実際にあったバグ**: 左⌘を使った直後の最初の右⌘ hold が黙って握り潰されていた。
      **外したときの意味:** 右⌘を押しても開始音が鳴らない/パネルが出ないなら、
      左⌘解放時の再武装（`hold_monitor.rs:190-195`）が効いていない。

- [ ] **(b) 左⌘↓ → 右⌘↓ → 右⌘↑ → 左⌘↑ → その後クリーンな右⌘サイクル（話す）**
      → 和音の間は**何も起きない**（開始音なし・パネルなし）。左⌘を離した後の2回目の右⌘は動く。
      **外したときの意味:** 和音の途中で録音が始まるなら、`foreign_held` の判定が緩い。

- [ ] **(c) 右⌘↓ → ⇧↓ → ⇧↑ → 右⌘↑ → 次の hold（話す）**
      → ⇧が加わった時点で hold が死ぬ（poison される）。その後の次の hold は動く。
      **外したときの意味:** ⇧を混ぜても録音が続くなら、割り込み時の poison が効いていない。

- [ ] **(d) クリーンな右⌘サイクルを2回（各回話す）**
      → 開始2回・終了2回ちょうど。

- [ ] **(e) 右⌘↓（話す）→ マウスクリック → 右⌘↑**
      → 終了は**1回だけ**（2回ではない）。
      **外したときの意味:** 終了が2回起きる/マイクを二重に閉じにいくなら、クリックの poison が
      すでに開いた録音を閉じ、その後の右⌘↑がもう一度閉じにいっている（`on_end` の二重呼び）。

- [ ] **(f) 右⌘を30秒間、離さずに握り続ける**
      → 手を離す入力が来なくても、上限タイマー（`max_hold_ms = 30_000`）で**マイクが自分で
      閉じる**。終了音が鳴り、パネルが Transcribing に変わる。
      **外したときの意味:** 30秒経ってもマイクが開いたままなら、`Timer::MaxHold` の配線が
      切れている。放置でマイクが開き続けるのはプライバシー上の欠陥。

結果:

```
(a) __  (b) __  (c) __  (d) __  (e) __  (f) __
```

## 3. `NSSound` をメインスレッド外で鳴らす

`ptt.rs::play_sound` は、エフェクト実行スレッド（メインスレッドとは限らない）から
`soundNamed:` + `play` を呼びます。`NSSound` の再生は独自のオーディオスレッドに投げられるので
安全なはず、というのが前提です。ハングしないこと・実際に鳴ることを確認します。

- [ ] システム音量を上げ、システム設定の「サウンドエフェクトを再生」を ON にする
      （`play_sound` は macOS 標準音を使うので、この設定に従う）
- [ ] 右⌘を押して話し、離す
- [ ] 開始時に **Tink** 音、終了時に **Pop** 音が鳴る
- [ ] 音が鳴らないことでセッションが**止まらない**（音が出なくても録音・応答は進む）

**外したときの意味:** ここで UI がフリーズする/セッションが進まないなら、`play_sound` が
呼び出しスレッドをブロックしている（`SAFETY` コメントの前提が崩れている）。

結果:

```
開始音: __  終了音: __  ハングの有無: __
```

## 4. 素の `NSWindow` に対する `float_on_all_spaces`

PTT パネルは、notch が使う reparent 済みの `NATIVE_PANEL` ではなく**素の通常ウィンドウ**です。
`float_on_all_spaces` は、notch の adoption モードで設定されたグローバル `PANEL_BEHAVIOR` を
読みます（`lib.rs:1360`）。既定では `257`（canJoinAllSpaces + fullScreenAuxiliary）が入りますが、
これが**素のウィンドウで本当に効くか**はこの環境では確かめられません。**最も失敗しやすい項目**です。

- [ ] 右⌘を押してパネルを出し、以下の各状況でパネルが**見える**ことを確認する:
  - [ ] **フルスクリーンのアプリ**の上（例: フルスクリーンにした Safari の上で右⌘を押す）
  - [ ] **2つ目の Space**（Mission Control で別デスクトップを作り、そこで右⌘を押す）
  - [ ] **外部ディスプレイ**（外付けモニタ側で右⌘を押す）

期待する結果:

- [ ] 3つの状況すべてでパネルが最前面に出る

**外したときの意味:** フルスクリーンや別 Space でパネルが出ないなら、素の通常ウィンドウが
`canJoinAllSpaces`（257）を window server に拒否されています。この場合、素のウィンドウには
`274`（moveToActiveSpace 系）が必要かもしれず、`float_on_all_spaces` を PTT パネル用に
調整する必要があります。参考として `SHOGUN_NO_NOTCH=1` で起動すると `PANEL_BEHAVIOR` が
`274`(move-to-active) に切り替わる（`lib.rs:254-255`）ので、素のウィンドウでの差を比較できます。

結果:

```
フルスクリーン上: __  2つ目のSpace: __  外部ディスプレイ: __
```

## 7. 【最重要の不変条件】音声ファイルが一切作られないこと

push-to-talk の 1 回の発話は「1 プロンプトになって消える」寿命のもので、**波形もテキストも
ディスクに残しません**（`buffer_sink.rs` の不変条件2）。会議レーンは `sessions` /
`transcript_segments` に書きますが、**PTT は絶対に書いてはいけません**。

- [ ] 右⌘を押して数語話し、離してエージェントに応答させる（1 セッション完了させる）
- [ ] 直後に、新しく作られたファイルが無いことを確認する:
      ```
      find ~/Library/Application\ Support/dev.shogun.spike -newermt '-5 minutes'
      ```
      → 音声ファイル（`.wav` / `.caf` / `.pcm` 等）が**1つも無い**こと
      （DB の WAL/ジャーナル等が出るのは可。音声波形ファイルが無いことを見る）
- [ ] DB は `~/Library/Application Support/dev.shogun.spike/memory.db`。**暗号化されている**
      （Keychain の `memory-db-key` で開く SQLCipher DB）ので、素の `sqlite3` では開けません。
      行が増えていないことは次のどちらかで確認します:
  - [ ] 簡易確認: PTT セッションの**前後で `memory.db` の mtime とサイズが変わらない**こと。
        ```
        stat -f '%m %z' ~/Library/Application\ Support/dev.shogun.spike/memory.db
        ```
        （PTT だけを行い、会議レーンを動かしていなければ、書き込みが無い＝更新されないはず）
  - [ ] 厳密確認: SQLCipher 対応 `sqlite3` に Keychain のキーを渡して開き、`sessions` /
        `transcript_segments` の `COUNT(*)` が PTT セッションの前後で**変わらない**ことを見る
        （会議レーンだけがここに書く）。キーの取り出し方は `lib.rs` の `DB_KEY_ACCOUNT`
        （`"memory-db-key"`）参照。

**外したときの意味:** 音声ファイルが残る、または PTT で `transcript_segments` に行が増えるなら、
不変条件2 が破れている（発話がディスクに漏れている）。これはプライバシー上の重大な欠陥で、
リリースをブロックします。

結果:

```
新規音声ファイル: __（無し=OK）
sessions 増分: __（0=OK）  transcript_segments 増分: __（0=OK）
```

## 11. SLO 実測表

実測して埋めてください。p50/p95 は複数回（10回程度）試行した分布から取ります。
初トークンの実測は `SloRegister::record_first_token_ms` に記録され、health ペインに出ます
（`submit()` が初デルタ到着時に記録）。

| 指標 | 目標 | p50 | p95 |
|---|---|---|---|
| hold → パネル表示 | ≤ 100ms | | |
| ASR 完了 → 初トークン | ≤ 1s（SLO-03） | | |
| hold 終了 → ASR 完了 | （目標なし・実測を記録） | | |
| 常駐 hold monitor のアイドル CPU 増分 | （目標なし・実測を記録） | | |

- [ ] hold → パネル表示: 押してからパネルが出るまでの体感/計測
- [ ] ASR 完了 → 初トークン: 終了音（Pop）から応答の最初の文字が出るまで（SLO の肝）
- [ ] hold 終了 → ASR 完了: 離してから Transcribing が終わるまで（whisper の所要）
- [ ] アイドル CPU 増分: hold monitor（常時 `watch` が動く）を入れた状態と、
      アプリ非起動時の Activity Monitor 上の CPU 差

**外したときの意味:** 「ASR 完了 → 初トークン」が 1s を超えるなら SLO-03 未達。
ストリーミング（`complete_streaming`）が実際にはインクリメンタルに届いていない可能性を疑う
（最初のデルタが本文全部の到着後にしか来ていない）。

### 注意: health ペインの「First token」は2つの計測を混ぜている

health ペインの **First token** 行（`metrics.rs` の `SloRegister::first_token_ms`）には、
push-to-talk と**チャット**の両方が値を書き込みます:

- **push-to-talk**（`ptt.rs`）は本物の初トークン — 最初のストリーミングデルタが届くまで — を記録する。
- **チャット**（`shogun_chat`、`inline_source.rs:987-989`）は非ストリーミング経路なので、
  **応答全体**の所要時間を記録する（コメントで意図的だと明記されている: 「初トークンより厳しい
  値なので、これが通れば初トークンも通る」）。

つまりペインに出る p50/p95 は **push-to-talk 単独の値ではない** — チャットを使うとその分だけ
汚染されます。**信頼できる push-to-talk の初トークン値を取るには、隔離した計測をすること:**

- [ ] アプリを再起動する
- [ ] **push-to-talk だけ**を10回ほど使う（チャットには一切触らない）
- [ ] その状態で health ペインの First token 行を読む

**外したときの意味の切り分け:** この隔離計測で 1s を超えるなら、それは本物の push-to-talk の
SLO-03 未達（上の「外したときの意味」を参照）。一方、**チャットも使った混在セッション**で
1s を超えていても、それは push-to-talk のリグレッションとは限らない — チャットの応答全体時間が
混ざっているだけかもしれないので、隔離計測で取り直してから判断すること。
（根本対処として First token 行を push-to-talk 専用に分離するのは別途フォローアップ。）
